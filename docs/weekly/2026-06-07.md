# Week 3: Consolidating the Foundation, NAS Hardware, Monitoring, and Automation

*Covers roughly 14 May - 7 June 2026. Phase 1 is done; this is everything between a
working two-node cluster and the ZFS/Seafile build that opens June.*

This was a longer, more diffuse stretch: the "make the foundation solid and
observable" phase. I brought the desktop/NAS node (nebula) online through some
hardware pain, stood up real node-health monitoring in Grafana, wrote the
cluster power automation, and settled how I'd document the whole thing. By 7 June
I had a genuinely instrumented, manageable cluster ready for the ZFS layer.

## 2. nebula: acquiring and reviving the desktop/NAS node

The third node, **nebula**, is a second-hand desktop: **i7-6700K, GTX 1080,
24GB RAM, Asus Z170 Pro**. It doubles as the ZFS NAS and the Docker Compose host.
Getting it running was the most hands-on hardware episode of the whole build.

### The boot-failure saga

After disassembling it for cleaning, it wouldn't even POST. After dealing with 
some minor hardware issues, we finally managed to boot into BIOS. Then comes booting
into Windows: literally a Windows logo and then a black screen thereafter, and an 
Ubuntu Server installer via a flash drive crashed mid-install. 

I replaced the CMOS battery and slowly realised that the issue was not the hardware.
Though old, all of them were functional and the issue with installation is the switching
of graphics output from the GPU to CPU mid install due to a lack of nvidia graphics drivers
before we reach our OS. This is fixable by adding one single line into the edit menu
of the GRUB installer.

``` bash
nomodeset
```

### BIOS tuning for a 24/7 NAS

By right the BIOS should be tuned to ensure lower power consumption. But honestly
most of the tuning causes system instability and barely any reduction in power 
consumption. I've come to realise the main power guzzler is the motherboard with
all of its I/O components, especially the GPU.

You should definitely disable overclocking and minimally tune down the frequency.
Most of the experimentation here is a time sink and only should be attempted with
much more free time.

## 3. Node-health monitoring in Grafana

With kube-prometheus-stack installed, I built a real node-health dashboard, the
first serious observability work. This session also taught me a pile of
cluster-access mechanics that became permanent knowledge.

### Access mechanics learned the hard way

- **`localhost` vs LAN IP over SSH.** Port-forwarding a ClusterIP service and
  trying to reach it was confusing until I understood: `kubectl port-forward
  --address 0.0.0.0 …` binds to all interfaces so I can hit it from Windows at the
  node's LAN IP (e.g. `http://192.168.1.250:9090` for Prometheus). ClusterIP
  services aren't reachable externally without this. (This is the same
  SSH-localhost trap that recurs throughout the project.)
- **The kubeconfig permission fix.** `/etc/rancher/k3s/k3s.yaml` is root-only by
  default. Fix: `chmod 644` *and* add **`--write-kubeconfig-mode=644`** to the K3s
  systemd service so it survives restarts. This is what later lets me scp the
  kubeconfig to my laptop without sudo.
- Grafana confirmed on `svc/kube-prom-grafana` (ClusterIP :80), reached via
  port-forward `8080:80`.

### Sensor discovery: what the hardware actually exposes

Rather than guess PromQL, I queried Prometheus to see which sensors returned data:

- **CPU temp** works via `node_hwmon_temp_celsius` with the `coretemp` chip.
- **CPU voltage does not exist**: `node_hwmon_in_volts` returned nothing; these
  boards don't expose voltage rails. Dropped from scope entirely.
- **RAPL power** (`node_rapl_package_joules_total`) returned nothing from the
  container despite working at the host (`sudo cat
  /sys/class/powercap/intel-rapl:0/energy_uj` gave a real value). The fix:
  node-exporter needs `runAsNonRoot: false` / `runAsUser: 0` in its securityContext
  to read RAPL. (This is not as useful as you think. CPU power is not significant
  compared to I/O power draw in our case.)
- **A real thermal finding:** deus's (M910q) NVMe `temp2` sensor read **~89.85°C at
  idle**, a genuine concern flagged for airflow attention. This is the earliest
  signal of the "deus runs hot" theme that later drives keeping Longhorn replicas
  off it.

Delivered: working PromQL for CPU usage/temp, RAM, network (with virtual-interface
filtering), disk read/write, NVMe temp, plus a `PrometheusRule` with alerts (CPU
critical >90°C for 2m, NVMe warning >80°C for 5m), wired to both Alertmanager and
Grafana alerting. GPU panels deferred (legion's dGPU was disabled via envycontrol).

## 4. Cluster power automation

Because legion was still a come-and-go node, I wrote a pair of scripts to bring the
cluster up and down cleanly: **`cluster-shutdown.sh`** and
**`cluster-powerup.sh`**. These went through several meaningful refinements:

- **Shutdown** (runs on deus): SSH into legion, poweroff, then shut down deus
  itself, but **abort rather than proceed if the worker can't be confirmed
  offline**, so deus never shuts down while a worker is stranded. A nuance:
  `sudo systemctl poweroff` over SSH usually drops the connection before returning
  a clean exit code, so a **ping-based verification loop is the authoritative
  check**, not the SSH exit status.
- **Powerup:** send a **Wake-on-LAN** magic packet to legion, then poll the K3s API
  (`kubectl get node`) until legion reports `Ready`, a real readiness check, not
  just a ping. This is not really working and further testing needs to be done.
- **Least-privilege security model:** rather than blanket passwordless sudo, scoped
  `/etc/sudoers.d/cluster-poweroff` entries granting `NOPASSWD` only for
  `systemctl poweroff` on both machines, plus a dedicated SSH key
  (`~/.ssh/cluster_shutdown`) with `BatchMode=yes` so it fails cleanly instead of
  hanging on a prompt.

## 5. Documentation strategy

I also settled *how* I'd record all this, which is why these very logs exist. Two
categories:

- **Decision logs**: short markdown entries written *at decision time*, capturing
  the reasoning behind architectural tradeoffs. These live in a `/docs` folder.
- **Polished technical write-ups**: the "how" and lessons learned, meant as
  portfolio pieces.

**GitHub is the non-negotiable source of truth** for all of it. Self-hosting the
docs on the cluster is a Phase 2-3 milestone, *not* the primary home, because
cluster downtime during learning makes self-hosting unreliable as the sole
destination. Plan: GitHub as canonical, GitHub Pages as fallback, and eventually a
Hugo/Astro static site containerized and deployed through the CI/CD pipeline, so
the *deployment pipeline itself* becomes a portfolio artifact.
