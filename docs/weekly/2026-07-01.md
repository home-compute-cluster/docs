# Week 8: The Two-Plane Ingress, Wildcard TLS, and Adopting Everything into GitOps

*Covers roughly 27 June - 1 July 2026.*

This was the week the network architecture actually took its final shape. Up to
now I had "Cloudflare for public, WireGuard/Tailscale for bulk" as a *direction*.
This week I turned it into a concrete two-plane ingress split with real wildcard
TLS, moved secrets into Git properly, and started dragging my hand-installed Helm
releases under ArgoCD so nothing is untracked.

## 1. The VPS relay question, and why I probably don't need it

I started the week pricing a cheap VPS to run a WireGuard relay, in case the
locked Singtel ONR wouldn't forward inbound ports. What I learned about picking
one: for a WireGuard relay, **CPU and RAM barely matter** (it runs fine on
512MB); the only things that matter are a **high/unmetered bandwidth allowance**
and a **1Gbps+ port**. BuyVM's Slice 512 (~$2/month annual, genuinely unmetered
on 1Gbps) was the pick, with the caveat that stock is often unavailable. Also:
put the VPS in an **Asian region**, not the US, or I'm compounding trans-Pacific
latency from Singapore.

But the real conclusion was: **I probably don't need the VPS at all.** My Singtel
line has a real routable public IP (confirmed back in Week 3), so if the ONR
forwards UDP 51820 to deus, a **direct** WireGuard config is strictly better and
free. Try the direct path first; treat a `wg show` handshake as proof.

## 2. The two-plane ingress split (the big architectural decision)

This is the one that mattered. I set up Tailscale for private access and, in
doing so, settled the clean split I'd been circling:

- **`*.packetcraft.dev`**: public, via Cloudflare Tunnel (outbound-only, no
  inbound port).
- **`*.lab.packetcraft.dev`**: **tailnet-only.** Grey-cloud (DNS-only) A records
  in Cloudflare pointing at the private/Tailscale IPs, plus a Tailscale split-DNS
  entry forwarding the zone to 1.1.1.1 so the OS resolver actually works.

The correction that shaped this: **MagicDNS can't hold arbitrary custom
records.** I'd assumed I could just use Tailscale's own DNS for the `lab.` names,
but it doesn't work that way, so Cloudflare public DNS serves as the record
store even for the tailnet-only names. The records just resolve to private IPs
that only mean anything if you're on the tailnet.

Two more decisions here:

- **Seafile stays on Cloudflare Tunnel**, not Tailscale. It's a >6-user use case
  and that doesn't fit the tailnet model (I'd have to enroll every user's
  device). Public tunnel is the right call for it.
- The `lab.` zone **needs a real Let's Encrypt wildcard cert**, not self-signed,
  because `.dev` is HSTS-preloaded; browsers hard-block plaintext HTTP with no
  click-through. Same HSTS lesson from the CI/CD week, now applying to the
  private plane too.

## 3. Wildcard TLS via cert-manager + Let's Encrypt DNS-01

To get that wildcard cert for `*.lab.packetcraft.dev`, I set up cert-manager with
a DNS-01 challenge against Cloudflare. This is where I hit the most confusing
debugging loop of the week, and the lesson is worth writing down carefully:

**The Cloudflare API token SealedSecret has to live in the right namespace, and
"the right namespace" is different for the issuer input vs the cert output.**

- The **API token** (the issuer's *input*) must be in the **`cert-manager`**
  namespace, because cert-manager runs with
  `--cluster-resource-namespace=$(POD_NAMESPACE)`, so a ClusterIssuer looks for
  its credentials there.
- The **cert output** (for the TLSStore) lives in **`kube-system`**.

I had the token sealed for the wrong namespace, so the DNS-01 challenge kept
failing. Different rules for issuer-input vs cert-output is the thing to
remember. (SealedSecrets are encrypted per namespace+name, so a namespace
mismatch = decryption failure, full stop.)

Also, embarrassingly simple: at one point the **SealedSecret file was generated
but never `kubectl apply`'d.** Generating the sealed file isn't the same as
applying it. Easy to lose an hour to that.

## 4. Sealed Secrets: secrets in Git, done right

Tied to the TLS work, I leaned into Sealed Secrets as the way to keep credentials
in Git safely. The controller encrypts `SealedSecret` objects that only the
in-cluster controller can decrypt, so they're safe to commit. Three disciplines
this demands:

- **Namespace scoping**: encrypted per namespace+name; mismatches silently fail
  to decrypt (exactly what bit me with cert-manager).
- **`existingSecret` pattern**: migrate service credentials to reference a secret
  instead of letting the Helm chart own them. Grafana's admin password is the
  poster child (more on that in Week 6/7).
- **Back up the controller's private key**: outside the cluster *and* outside
  Git. If I lose it, every sealed secret is unrecoverable. The command:
  `kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml`.

I confirmed I don't need a heavier secrets manager (Vault, External Secrets
Operator) yet; those only earn their place if I need dynamic secrets, rotation,
or audit logging. For obsync's Postgres creds and per-device tokens, Sealed
Secrets is right.

## 5. Adopting hand-installed Helm releases into GitOps

I had installed kube-prometheus-stack and ArgoCD itself by hand. This week I
started adopting them into ArgoCD Applications so they're tracked, not drift.

A couple of concrete snags:

- **Release-name mismatch nearly created a duplicate.** The live
  kube-prometheus-stack release is actually named **`kube-prom`**, not
  `kube-prometheus-stack`. Adopting under the wrong name would have stood up a
  second, conflicting release. Match the existing release name exactly.
- **The ArgoCD `server.insecure` flag goes under `configs.params`**, not under
  `server:`. I had it in the wrong place. (It needs to run insecure/HTTP so
  Traefik + Cloudflare own TLS, otherwise redirect loop, same lesson as the
  CI/CD guide.)

### The GitOps pattern this clarified

This is where I nailed down the repo conventions:

- **Pattern B (upstream Helm charts):** just an `argocd/<svc>.yaml` Application
  file. **No `apps/<svc>/` folder needed.**
- **`apps/<svc>/` only exists when I author manifests myself.**
- **Multi-source** when a chart needs my own values + optional custom manifests:
  chart repo + a `$values` ref from `homelab-cicd-config` + an optional custom
  manifests source.

## 6. Cleanup: orphaned nginx and guestbook

Housekeeping. The old `nginx` and `guestbook` test workloads were still running
even though I thought I'd removed them. The lesson: **deleting an ArgoCD
Application does not cascade-prune the live resources** unless specific conditions
are met, so they were orphaned plain Kubernetes objects with no controller
recreating them (and none resurrecting them either, since the Applications were
already gone). I confirmed only `budget-app-dev` and `code-server` remained as
Applications, then cleaned up with `kubectl delete ns nginx guestbook` and
checked the `apps/nginx/` and `apps/guestbook/` folders were gone from the config
repo so nothing could accidentally resurrect them.

## What I locked in this week

- **Two-plane ingress:** `*.packetcraft.dev` public via Cloudflare,
  `*.lab.packetcraft.dev` tailnet-only via grey-cloud records + Tailscale
  split-DNS. MagicDNS can't hold custom records; Cloudflare is the record store.
- **Wildcard Let's Encrypt cert** for the `lab.` zone via cert-manager DNS-01. The
  API token goes in `cert-manager`; the cert output in `kube-system`.
- **Sealed Secrets** as the secrets layer, with the private-key backup rule and
  the `existingSecret` migration pattern.
- **Pattern B / multi-source GitOps conventions** written down. Adopting kube-prom
  (as `kube-prom`) and ArgoCD into tracked Applications.
- **Orphan cleanup** done; learned that deleting an Application is not the same as pruning its
  resources.
