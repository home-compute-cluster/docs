## 2. The portfolio site: planning my first real application

I proposed a portfolio site (frontend + Go backend + database) as the first
real app. This got endorsed as a strong first project: it does double duty as a
deployment exercise *and* a Go learning vehicle, and the backend complexity is
intentionally low (a few JSON endpoints) so I can focus on Go the language rather
than distributed-systems correctness.

The deliberate sequencing decision: **portfolio site before obsync.** obsync
layers Go + Postgres + a hand-written sync protocol all at once, too many new
problems simultaneously. The portfolio site lets me learn the deployment shape
with low stakes first.

How the pieces map to my patterns:

- **Frontend** → built-from-source (Hugo/Astro noted earlier), its own repo + CI.
- **Go backend** → built-from-source, its own repo + CI.
- **Postgres** → off-the-shelf **Pattern B** (manifest + ArgoCD Application, no
  CI).

Left open at the time: the rendering approach: static frontend + separate Go
JSON API, vs server-side rendering in Go (templ/html-template), vs an SPA calling
a Go JSON API. (This gets picked up when I actually deploy Postgres in Week 7.)

## 3. WireGuard: finally, root access on the ONR

The big networking unblock. I found a **root-level admin account on the Singtel
ONR** that exposes DHCP, static IP reservation, and port forwarding, the exact
controls I'd been locked out of.

I sorted out a conceptual confusion first: **IP routing (static routes between
subnets) is not the same as port forwarding/NAT (exposing an internal host to the
internet).** I'd been conflating them. What I needed was port forwarding.

The exact rule: **UDP, port 51820** external and internal, targeting **deus**
(selectable directly from the ONR's client dropdown now that static reservations
are done), on the correct WAN interface (`1_TR069_INTERNET_R_VID_10`). The
prerequisite is verifying that interface carries the real public IP, not a
carrier-NAT address. Definitive test: `sudo wg show` on deus from a device off the
LAN (phone on mobile data) showing a completed handshake.

I paused to think about the **security** of opening a port, and came away
reassured: forwarding a single UDP port to WireGuard is about the lowest-risk
exposure there is. WireGuard is **cryptographically silent to unauthenticated
packets**: indistinguishable from a closed port to a scanner, no banner, no
fingerprint, minimal audited codebase. The residual risks are (1) key management
on client devices (a phone with a WireGuard config is effectively a LAN key), and
(2) not forwarding *additional* ports beyond the single WireGuard entry. Also
worth confirming the ONR's stateful firewall stays active and the forward is an
*exception* to it, not a symptom of a broader bypass.

End state of the network stack: **Cloudflare Tunnel for public services
(outbound-only), WireGuard on UDP 51820 for private high-throughput admin
access.** Both feeding Traefik.

## 4. Storage hardware: sourcing Longhorn disks

Longhorn can't use ZFS (established in Week 4), so I needed dedicated disks. I
worked through three options for getting them:

1. **Claw back space from nebula's ZFS mirror**: rejected. **ZFS doesn't support
   in-place vdev shrinking**, so this means either breaking the mirror (killing
   redundancy) or a full backup-destroy-restore with ongoing IOPS contention.
   Neither fits an architecture whose whole point is data safety.
2. **Buy new drives**: the sensible default.
3. **Used drives**: where I actually landed.

A couple of corrections I picked up while drive-shopping:

- The **WD Red SA500** is *not* DRAM-less (I'd initially thought so and corrected
  it); it uses a Marvell controller with TLC NAND and does have DRAM. It's a
  NAS-rated drive built for 24/7, which is a genuinely better replica posture than
  a consumer SSD.
- **NVMe M.2 drives use PCIe lanes, not SATA ports**, so adding NVMe doesn't cost
  me a SATA port. NVMe is a real option, not a compromise.
- The meaningful drive filter isn't "has DRAM" alone; it's **"DRAM or HMB + TLC
  NAND."** QLC is more harmful than DRAM-absence for sustained Longhorn
  replication writes.

Then the plan changed for the better: **I got three used 256GB M.2 NVMe SSDs
(Intel + WD, both with DRAM) for free from my company's IT department.** 256GB is
plenty per node since bulk data lives on ZFS. Plan: two drives across **deus and
nebula** for replica count 2 (the redundancy floor), third as a cold spare.

*(Note: this "deus + nebula" replica plan shifts again in Week 7; deus ends up
with no replicas due to its overheating, so the targets become nebula + legion.)*

I also worked out the **used-drive validation workflow** for the free SSDs:
`smartctl -a` (watch Percentage Used, Available Spare, Media/Data Integrity
Errors, Critical Warning) → non-destructive `badblocks -sv` → destructive
`badblocks -wsv` to exercise every cell → re-read SMART to confirm no
degradation. And verify which M.2 slots are actually free first: **deus has only
one M.2 slot** and it may already hold the OS drive.

## 5. The observability grind

The longest, most frustrating thread of the week. I was building a proper
"Homelab: Node Overview" Grafana dashboard on kube-prometheus-stack (chart
v85.0.2, release `kube-prom`, values in `apps/monitoring/values-monitoring.yaml`,
managed as a multi-source ArgoCD Application).

### Getting metrics flowing

- Dashboard 237 was empty because of **stale metric names**: the imported
  dashboard referenced old names.
- Enabled **hardware temperature monitoring** via the `hwmon` collector +
  `coretemp` kernel module.
- Hit a **many-to-one join error** on `node_hwmon_temp_celsius`: the fix was
  joining `on(chip, instance)`, not just `on(chip)`. And I had to filter
  `chip_name="coretemp"` because `max(node_hwmon_temp_celsius)` was otherwise
  grabbing the hottest sensor of *any* hardware, not the CPU cores.
- Confirmed chip names per node: all three have `coretemp` for CPU; nebula also
  has `asus` (eeepc_wmi) and `nvme`; deus has `acpitz` and `nvme`; legion has
  `pch_cannonlake`, `iwlwifi_1`, `adp0`.

### GPU metrics

Set up **nvidia_gpu_exporter** (utkuozdemir, v1.2.1) as a **Compose service on
nebula** (since the GTX 1080 lives on nebula, the Compose host). Metrics come out
under the `nvidia_smi_*` prefix. Confirmed names:
`nvidia_smi_utilization_gpu_ratio` (a **ratio**, needs `* 100`),
`nvidia_smi_temperature_gpu`, `nvidia_smi_power_draw_watts`,
`nvidia_smi_memory_used_bytes` / `_total_bytes`. To scrape a Compose service from
in-cluster Prometheus, I made a **`ScrapeConfig` CRD** in a separate
**`monitoring-extras`** ArgoCD Application, with a static `instance="nebula"`
label that landed correctly on the GPU metrics. Built the unified dashboard with a
`$node` template variable (CPU, RAM, temp, disk, network) plus a GPU row scoped to
nebula.

### The ArgoCD CRD mess (still not fully resolved)

This is the ugly part, and it's a family of related problems:

- I'm on **ArgoCD v3.4.3, which has a known h2c port-forward bug** making the CLI
  unreliable, which made everything else harder to debug.
- A persistent **`ComparisonError`** on the kube-prom Application because
  `readOnlyRootFilesystem` wasn't in ArgoCD's client-side structured-merge diff
  schema.
- **App-level `ServerSideApply=true` collides with ArgoCD's controller-injected
  `syncStrategy.apply.force`**: they're mutually exclusive at the apply level. A
  patch I tried that included `syncStrategy.apply.force` got stuck in the
  automated retry loop and had to be cleared by disabling automation, removing the
  `/operation` field, and re-syncing.
- The session ended mid-resolution with the CRDs (thanosrulers, alertmanagers,
  prometheusagents, scrapeconfigs, alertmanagerconfigs, prometheuses) failing on
  **`metadata.annotations: Too long: may not be more than 262144 bytes`**, the
  canonical kube-prometheus-stack + ArgoCD problem, caused by **client-side apply
  storing last-applied-configuration in an annotation** that blows past the 262KB
  ceiling.

The end-state I identified (but hadn't fully committed): **resource-level**
`argocd.argoproj.io/sync-options: ServerSideApply=true` annotations on the CRDs
(via `crds.annotations`) and the node-exporter DaemonSet (via
`daemonsetAnnotations`), **no app-level SSA**, plus `ignoreDifferences` on the
relevant fields. (This gets refined further in Week 7 when I discover the chart
version doesn't even *have* a `crds.annotations` injection point.)

## 6. Reclaiming under-provisioned disk space

A quick, useful find: every node only had ~100GB allocated to the OS despite
larger disks. Classic Ubuntu Server LVM under-provisioning: the installer makes a
volume group from the whole disk but only allocates part of it to the root LV.
Fix: `lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv` then `resize2fs` (ext4) or
`xfs_growfs` (XFS), both online-safe, no reboot. Since all three nodes share the
install config, this is a prime candidate for a retroactive Ansible playbook.
