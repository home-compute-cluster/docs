# Week 10: Longhorn Disks Live, the Database Lands, and the Loose Ends Get Tied

*Covers roughly 9 - 15 July 2026.*

If Week 9 was "get ready," this week was "actually do it." The Longhorn disks went
in, the observability CRD mess finally got resolved, the Grafana password loop got
killed properly, and (the milestone) the first real database landed on the
cluster via CloudNativePG, backups and all. Also confronted the uncomfortable
truth that deus is a single point of failure.

## 1. Longhorn disks physically installed and configured

The free NVMe drives from Week 9 went in. Final storage topology, per node:

- **deus**: 256GB NVMe is the OS drive; overheats; **no Longhorn replicas.**
  Scheduling disabled entirely; deus is compute/control only.
- **nebula**: got a **256GB WDC PC SN730 NVMe** dedicated entirely to Longhorn
  (no partitioning). Also has the 931.5G HDD and the two 3.6T ZFS pool drives, OS
  on sdd. Longhorn scheduling enabled **only** on the dedicated disk.
- **legion**: got a **500GB WD Red SA500 SATA SSD** (`/dev/sda`), **partitioned**:
  ~400G formatted ext4 directly (no LVM) at `/var/lib/longhorn-disk-sda` for
  Longhorn, ~65G as a separate `spare-vg` on `/dev/sda2` for general use.

Key config points:

- **2-replica**, targets are **nebula's SN730 + legion's WD Red partition**,
  meaning **zero placement slack** with only two targets. (I corrected an earlier
  cached assumption that deus and nebula were the replica pair; deus has *no*
  replicas.)
- On every node, the default `/var/lib/longhorn` OS-disk path is
  scheduling-disabled; only the dedicated disks schedule.
- The WD Red SA500 being **NAS-rated for 24/7** meaningfully improves the replica
  posture on legion.

A couple of hands-on gotchas installing the drives:

- On nebula's NVMe, `lsblk` showed no partitions but `mkfs.ext4` detected a
  **leftover GPT table from the drive's previous life**: had to `wipefs -a
  /dev/nvme0n1` first. Correct sequence: `wipefs -a`, then `mkfs.ext4 -L
  longhorn-nebula`, then mkdir, then `blkid`, then an fstab entry (by UUID, with `nofail`), then
  `mount -a`.
- Interpreted the SMART check on the used NVMe: PASSED, 0 media/data integrity
  errors, 100% available spare, 20% wear (~33TB written), 857 unsafe shutdowns
  (cosmetic, not corruption). Healthy enough.

## 2. Bringing Longhorn itself under GitOps

I adopted the existing Longhorn v1.12.0 Helm install into an ArgoCD Application
**without reinstalling**: the diff showed only ArgoCD tracking-id annotation
additions, no pod restarts, confirming a safe adoption. This is the same "adopt,
don't reinstall" pattern I used for kube-prom in Week 8.

## 3. Killing the Grafana password loop for good

The Grafana admin password kept resetting on every ArgoCD sync. Root cause, stated
cleanly: the Grafana Helm subchart **generates a random password at
`helm template` time**, and `selfHeal: true` then stamps that over the live
secret every reconcile. Any credential the Helm chart owns will churn under
self-heal; that's the general principle.

The fix (finally committed this week): a **SealedSecret named `grafana-admin`** in
`apps/monitoring-extras/`, with `values-monitoring.yaml` pointing at it via
`grafana.admin.existingSecret: grafana-admin` (`userKey: admin-user`,
`passwordKey: admin-password`). That removes password ownership from the Helm
chart entirely and makes the SealedSecret the git-declared source of truth ArgoCD
won't churn.

Two caveats I noted: Grafana only reads `admin-password` on **first boot / DB
init**, so if the admin user already exists I may need
`grafana-cli admin reset-admin-password` or a PVC wipe; and the Sealed Secrets
private-key backup must be current before committing. The secret didn't appear at
first but resolved on its own once the ArgoCD poll caught up, a **timing** issue,
not a config error (a recurring theme, and an argument for finally fixing the
webhook).

## 4. The ArgoCD CRD `Too long` problem: resolved

I finally closed out the CRD annotation mess from Week 9. Inspecting the actual
chart tarball revealed the real situation: **kube-prometheus-stack 85.0.2 ships
its CRDs as raw untemplated files with no `crds.annotations` injection point**,
so the resource-level SSA-via-values approach I'd planned in Week 9 was
*impossible* for this chart version.

The correct fix turned out to be simpler: the **app-level `ServerSideApply=true`
already sat in `argocd/kube-prometheus-stack.yaml` in Git; it just was never
applied to the live cluster**, because `argocd/` isn't watched by any app-of-apps
and requires a manual `kubectl apply`. So I applied that file and stripped the
stale `kubectl.kubernetes.io/last-applied-configuration` annotation off the six
affected CRDs.

Then one last sync failure: `failed to create typed patch object` on the
node-exporter DaemonSet, because `readOnlyRootFilesystem` was set inside the
**pod-level** `securityContext` where it isn't a valid schema field. Client-side
apply had silently tolerated it; **SSA's strict schema enforcement surfaced it.**
Removed that one line (the chart's `containerSecurityContext` already sets it
correctly by default).

**The recurring structural lesson from all of this:** the absence of an
app-of-apps watching `argocd/` is a silent-drift source in my setup: Application
definitions committed to `argocd/` don't take effect until I manually apply them.
That's a real gap to close.

## 5. The database lands: CloudNativePG

The milestone of the week: the first real stateful workload. I deployed
**PostgreSQL via the CloudNativePG (CNPG) operator** for the portfolio site.

The mental model that made it make sense was a **two-layer control loop**: ArgoCD
owns the `Cluster` CR (the desired state in Git), and CNPG owns the actual
pod/PVC/Secret (reconciling the database to match the CR). Decided strategically:
**Postgres-via-CNPG is the default for all K8s database workloads**, one `Cluster`
CR per application (not a shared instance), unless a workload ships its own
embedded store.

Real issues diagnosed and fixed along the way:

- **CRD-not-found** at first because I'd put the `Cluster` CR in `argocd/cnpg.yaml`
  instead of a proper Application CR.
- **`kubectl apply` structural error** switching from `source` to `sources`
  (single- to multi-source): needed `--server-side`.
- **Port collision**: the kubectl port-forward clashed with a Windows-installed
  PostgreSQL service on 5432.
- **pgAdmin instability** over port-forward: port-forward just isn't suited to
  GUI clients holding persistent connections.
- **Backup credential error**: I sealed the Garage key's *friendly name*
  (`cnpg-key`) instead of its actual key ID (`GK...`).
- A **kubectl ambiguity** worth remembering: after adopting Longhorn,
  `kubectl get backup` resolves to `backups.longhorn.io`, not the CNPG resource,
  so I need `kubectl get backups.postgresql.cnpg.io` explicitly now.

### Backups: Garage over MinIO

For CNPG's S3-compatible backup target I started with **MinIO** but switched to
**Garage** after finding MinIO's community edition **stripped access-key
management from the UI** after a mid-2025 product pivot. Garage went up via Docker
Compose on nebula, data on `tank/backups/garage` (ZFS), `replication_factor = 1`,
a `cnpg-backups` bucket granted to a dedicated key (`garage key create` +
`garage bucket allow`). The CNPG `Cluster` CR got a `barmanObjectStore` pointing
at `http://192.168.1.248:3900`, WAL compression on, and a `ScheduledBackup` CR for
3am daily.

## 6. Confronting the deus single point of failure

Installing storage made me face that **deus is a SPOF for the K3s control
plane**: single-server embedded etcd. I'm considering buying a mini PC. The
important correction I absorbed: **two K3s server nodes with embedded etcd is
worse than one** (no quorum, an even number can't break ties). Genuine
control-plane HA needs **three server nodes.** So a single new mini PC is best
used as a **worker** (to reduce blast radius and migrate pinned services off
deus), not as a stepping stone to HA. The endgame framing: **two or three
dedicated mini PCs as the server/etcd tier**, with the current nodes as workers.

## 7. Smaller things this week

- **Dev container scale-to-zero.** To turn `code-server` off when unused without
  self-heal fighting me: the clean answer is **`ignoreDifferences` on
  `/spec/replicas`** so "off" is the declared default and manual `kubectl scale`
  persists. `replicas: 0` in Git gets reverted by self-heal; KEDA scale-to-zero is
  deferred (poorly suited to code-server's long-lived tunnel connection). Scale to
  zero is safe because the PVC (including tunnel auth at `~/.vscode/cli`) persists
  across restarts.
- **Headlamp** deployed via ArgoCD with a long-lived ServiceAccount token
  (`headlamp-admin` bound to `cluster-admin`), the chart's ingress disabled, replaced
  with a hand-authored Traefik IngressRoute at `headlamp.lab.packetcraft.dev`.
  This is where the **ArgoCD-not-auto-syncing-on-push** problem got pinned down:
  it's the missing GitHub webhook (poll-interval lag). The webhook is the clean
  fix, contingent on the ArgoCD UI already being exposed through the tunnel.
- **Kubernetes dashboard chase.** Tried to add the official kubernetes-dashboard;
  its Helm repo 404'd and I burned time chasing non-existent OCI/GHCR paths (all
  403'd) before web search confirmed the HTTP repo is still the documented method.
  Pivoted to evaluating **kite** (`kite-org/kite`) instead: actively maintained,
  but a much heavier platform tool with **write capabilities, an AI agent that can
  mutate the cluster, and a SQLite+PVC requirement**. If I deploy kite it **must**
  stay on the tailnet plane (`*.lab.packetcraft.dev`) given those mutation powers.
  Left undecided pending read-only-vs-read-write scoping and whether to enable the
  AI agent. (Headlamp is the lighter option I actually deployed.)
- **Regenerated the Docker and K3s guides** to be generalized/reusable rather than
  project-specific, keeping some first-person voice in the K3s one for the
  genuinely non-obvious bits (the SSH-localhost trap, taint+toleration as
  attraction+permission, tunnel ingress as one pattern among several).
- **Secrets manager question settled again:** Sealed Secrets is enough; no Vault /
  ESO until I need dynamic secrets, rotation, or audit logging.
