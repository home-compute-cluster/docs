# Week 11: Backups, a Simpler Network, and a Six Day Empty Bucket

*Covers roughly 16 - 22 July 2026.*

This week was about making the things I had already deployed safe to keep. Backups
went in for everything that holds state, the MoCA hop disappeared from the network,
and this documentation site went live. It was also the week of the CNPG backup chase,
which turned a five line fix into several hours and finally made the ArgoCD webhook a
real priority.

## 1. Backups for everything that is not ephemeral

Anything that holds data I would miss now has a backup path. Longhorn volumes back up
to a target on nebula, and the portfolio database archives to Garage (more on that
below).

Setting up the Longhorn `BackupTarget` failed straight away:

```
failed to create typed patch object (longhorn-system/default;
longhorn.io/v1beta2, Kind=BackupTarget):
.spec.pollIntervalInSeconds: field not declared in schema
```

The field I had copied does not exist in the `v1beta2` API. The correct name is
`pollInterval`. A small thing, but a good reminder to check field names against the
CRD that is actually installed (`kubectl explain backuptarget.spec`) instead of
trusting an example.

## 4. The CNPG to Garage backup chase

**Goal:** WAL archiving and base backups from `portfolio-db` (CNPG) to Garage, the
S3-compatible store on nebula.

**Symptom:** the bucket had been empty for six days. The archiver was failing
continuously and the very first WAL segment had never shipped.

Some context first. I had started with MinIO, then switched to Garage after finding
that MinIO's community edition removed access key management from its web console in
its 2025 change of direction, leaving only the CLI. So the backup store was already
on its second implementation when this started.

The failures peeled back one layer at a time. Every one of them was the same shape:
the value that was live in the cluster did not match the value I intended.

1. **Sealed the key's name, not its ID.** I put `cnpg-key` (the name I gave the key)
   into the secret instead of the access key ID starting with `GK`. Garage replied
   `No such key: cnpg-key`. Fixed by resealing with the real values from
   `garage key info --show-secret`.
2. **A dangling secret reference.** I had renamed the secret from `minio-creds` to
   `backup-store-creds`, but the `Cluster` resource still pointed at `minio-creds`.
   It showed up as `secret not found` and then as a `cache miss`, because the
   archiver cannot build its environment when the credential lookup fails.
3. **Underscores in the name.** Fixing the reference, I typed `backup_store_creds`.
   Kubernetes names only allow lowercase letters, digits, hyphens and dots, so that
   could never match anything. Back to `backup-store-creds`.
4. **Region mismatch.** Once authentication worked, `HeadBucket` returned
   `400 Bad Request`. barman-cloud signs its requests for region `us-east-1`, while
   Garage defaults to a region called `garage`. Setting `s3_region = "us-east-1"` in
   `garage.toml` and restarting Garage fixed it, and the WAL flushed immediately.

The error moved cleanly down the stack: finding the secret, then a valid credential,
then S3 authentication, then region negotiation, then finally the write. Each fix
exposed the next layer.

### What I took from it

- **Name secrets after their role, not the product.** `minio-creds` became wrong the
  moment I switched to Garage, and that stale name caused two of the failures.
- **With Garage, seal the access key ID, not the key name**, and set the region to
  `us-east-1` so it matches what AWS client libraries expect.
- **`cache miss` in the CNPG archiver is not a caching bug.** It means an upstream
  credential or config lookup failed.
- **Every single one of these was correct in Git and wrong in the cluster.** Without
  the ArgoCD webhook, every step meant pushing, waiting for a poll, and checking by
  hand whether the change had landed. That is what made it take hours.
