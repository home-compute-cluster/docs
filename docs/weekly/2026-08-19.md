# Week 15: Monitoring Longhorn, and a Short Panic

*Covers roughly 13 - 19 August 2026.*

This week's focus was monitoring and alerting for everything deployed so far. The
first attempt, Prometheus monitoring for Longhorn, taught two things worth writing
down.

## 1. Nothing tracks `argocd/`

When I change anything under `argocd/`, the whole file has to be applied again by
hand, because nothing is watching that folder. The Application manifests in
`argocd/` track their counterparts in `apps/`, but nothing tracks the Application
manifests themselves.

This is the same gap that caused the CRD problem back in Week 10. It keeps catching
me, which is the clearest sign it needs a structural fix: an app-of-apps that watches
`argocd/`, so that committing an Application change is enough.

## 2. "Degraded" volumes that were never going to be healthy

Once the Longhorn dashboards were up, they showed the volumes as degraded and unable
to schedule. That caused a proper panic for a few minutes.

It turned out Longhorn wanted three replicas per volume, and only two nodes in the
cluster have Longhorn disks (nebula and legion). A volume that asks for three
replicas can never be fully healthy with two storage nodes, so the dashboard was
telling the truth about a setting, not about a failure.

The replica count needs to match the disks that actually exist. Two replicas is the
target here, and it has to be set both in Longhorn's default replica count setting and
in the StorageClass.

## Still open

- **App-of-apps** watching `argocd/`.
- **Set the Longhorn replica count to 2** everywhere it is read from.
- **Monitoring for the remaining services**, then alerting.
