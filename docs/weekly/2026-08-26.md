# Week 16: Monitoring Everywhere, and the First Shape of obsync

*Covers roughly 20 - 26 August 2026.*

This week went almost entirely into monitoring for the critical infrastructure
services, and it is finally done. I also started laying out obsync.

## 1. Monitoring and alerting for the core services

Dashboards and alerts are now deployed for:

- **Traefik**, since all traffic passes through it.
- **Longhorn**, for volume health and replica state.
- **CNPG**, for the database and its WAL archiving.
- **cert-manager**, so certificate renewals do not fail silently.
- **ArgoCD**, for sync and health status of every Application.

All of them use the template from Week 13, with each dashboard's JSON kept in a
ConfigMap. The alert rules went out together with the dashboards. Some thresholds
will probably need tuning once I see how noisy they are in practice.

> **Later note:** the rules were deployed, but Alertmanager was still routing every
> alert to a "null" receiver, so nothing actually notified anyone. That is why the
> September incidents were all found by eye. Alerts only started reaching a person
> once Discord routing went in.

## 2. obsync: the first design

I started the template for obsync. The first version is built around a single
authoritative source of truth: a data store that everything else reads from.

- **Backend:** a Go cron job that runs once a day, pulls changed data out of Canvas,
  and writes the diff into the data store.
- **Frontend:** an Obsidian plugin written in TypeScript that copies what is in the
  data store (or a cache of it) down to the client.
- **Sync model:** entirely pull-based. Canvas is the source of truth, and local
  changes in Obsidian do not sync back.

This is deliberately simple. It gets the pieces deployed and talking to each other
before I take on the much harder problem of real-time, two-way sync. It is the same
rule as always: one hard new problem at a time.
