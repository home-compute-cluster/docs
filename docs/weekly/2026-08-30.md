## 2. The surprise: the cluster was running on SQLite

The reason this took so long is that the cluster first had to be migrated from
**SQLite to etcd**.

I had not realised the original cluster was using SQLite at all. With a single K3s
server and two agents, K3s uses an embedded SQLite database by default, and nothing
about day-to-day use tells you that. SQLite cannot back a cluster with more than one
server, so before sol and opus could join, the existing server had to be converted.

K3s supports this in place: restart the existing server with `--cluster-init` to turn
on embedded etcd, then join each new server with `--server` pointing at it. All
servers need the same networking and feature flags, which is exactly the kind of thing
Ansible is good at keeping consistent.

If you want to check what your own K3s server is using, look in
`/var/lib/rancher/k3s/server/db/`. A `state.db` file means SQLite; an `etcd`
directory means embedded etcd.

## 3. Provisioning is now close to trivial

The good news is that adding a node is now easy. As long as a machine has:

1. an OS installed,
2. SSH access, and
3. a static IP set in netplan,

the Ansible playbooks take it the rest of the way into the cluster.

The exception is **Tailscale**, which is still configured by hand on each node. It was
complicated enough to automate that I left it manual for now. (That decision comes
back to bite in the next two weeks.)
