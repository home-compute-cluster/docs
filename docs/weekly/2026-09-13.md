# Week 19: Firefighting, kube-vip, and kured

*Covers roughly 7 - 13 September 2026.*

This week was pure firefighting. A kube-vip change on Tuesday was followed by the
worst outage the cluster has had so far, and fixing it took most of the week and a
monitor and keyboard plugged into deus. Once it was over, though, the cluster ended the
week in the most complete state it has ever been in.

## 1. The kube-vip deployment and the deus outage

On Tuesday I deployed kube-vip to give the `*.lab` services one shared ingress address
instead of pointing DNS at individual nodes. Shortly afterwards deus stopped responding
to everything: the Kubernetes API, SSH, even ping. It was also unreachable for
investigation because, again, it is the only Tailscale subnet router.

Diagnosis and repair took several days and needed a direct console connection. The
short version of what happened:

- deus had Tailscale's `--accept-routes` turned on while it was also advertising the
  LAN subnet. kube-vip's change to the network interface made Tailscale reconfigure
  itself and install that LAN route pointing into the tunnel.
- From then on, deus could send traffic but every reply to a LAN host went into the
  tunnel instead of back out the network card. SSH, ping, the API and etcd all failed
  the same way.
- A second, unrelated problem turned up during the fix: `ufw` was active on deus when it
  should not have been, and it was blocking etcd traffic from sol and opus.
- etcd held quorum on sol and opus the whole time, so no data was lost, but the cluster
  spent nearly four days one failure away from a restore.

Both root problems existed because Tailscale and the firewall were set by hand on each
node instead of through Ansible.

Full write-up: [deus control-plane outage](../postmortems/2026-09-08-deus-control-plane-outage.md).

## 2. What did get finished

With the outage behind it, the week still delivered two things:

- **kube-vip is deployed**, with a shared ingress path across the control-plane nodes.
- **kured is deployed.** It watches for nodes that need a reboot after OS updates and
  reboots them one at a time, cordoning and draining each first. I will see next week
  whether it actually behaves.

If kured works as intended, the cluster is essentially done. From here, changes should
be small upgrades rather than new building blocks, and there will be no more physical
hardware changes for a long while.

## 3. obsync begins properly

With the infrastructure settled, obsync gets my full attention. The first version,
where clients pull data manually, is being tested this week. Development of the actual
sync version starts next week, once the requirements and architecture are fully clear.
