    Week 1: The Genesis, Physical Network and Getting the Layer-1 Right

    Covers roughly 6–10 May 2026. Before this, there was no cluster, just a spec and a room with a coax outlet.

    This is the true beginning. Before any OS, before K3s, before a single line of YAML, I had to solve a dumb but blocking physical problem: my room has no Ethernet port, only a coax outlet. Everything else in this entire project sits on top of the network I built in this first stretch, so it's worth writing down properly.

    1. The problem: getting a wired LAN into a room with no Ethernet

    My room in the condo has a coax outlet but no RJ45. WiFi was a non-starter for a cluster: it adds latency, drops packets, and makes inter-node K3s communication unreliable. I needed real wired Ethernet to the nodes. The answer was MoCA (Multimedia over Coax): adapters that tunnel Ethernet over the existing coaxial wiring already in the walls.

    The coax splitter question

    The first real snag was the house's existing coax splitter. It was rated only 5–1000 MHz, and MoCA 2.5 operates well above that (up into the ~2.6 GHz range). A splitter that cuts off at 1 GHz will simply kill the MoCA signal. So I planned to replace it with a MoCA-rated splitter (10 MHz–2.6 GHz): a single 1→6 unit with power-pass ports, good port-to-port isolation, and low insertion loss, compatible with MoCA 2.5/3.0.

    The other physical-layer detail: a PoE filter (Point-of-Entry filter) between the router side and the coax input. This keeps the MoCA signal inside the house (reflecting it back rather than letting it leak out to the street / neighbours), which both improves signal quality and is good practice for security. Worth confirming you can swap a condo splitter yourself; in my case, yes.

    2. The physical topology

    Four cables, one clean chain. This is the layer-1 map the whole cluster runs on:

    Router (main hall)
  │  Ethernet
MoCA adapter #1  ── coax ──▶  (wall coax wiring)
                                    │
                              MoCA adapter #2 (my room)
                                    │  Ethernet
                              Omada 8-port switch
                                 │        │        │
                              node       node     node

    Concretely:

    1. At the router: Ethernet from a router LAN port into MoCA adapter #1; coax from adapter #1 into the wall outlet.
    2. In my room: coax from the wall outlet into MoCA adapter #2; Ethernet from adapter #2 into any port on the TP-Link Omada 8-port easy-smart switch.
    3. From the switch: one Ethernet run to each node.

    The switch is a managed (easy-smart) unit deliberately: it gives me VLANs and QoS later for the "isolate cluster traffic" learning exercise, but I explicitly deferred all VLAN config. At this stage it's just a flat switch. Get layer-1 working first; segment it later.

    Verifying it worked

    Dead simple: once the MoCA adapters sync (1–2 minutes, watch the link LEDs), every node pulls a DHCP address and reaches the internet. ping 8.8.8.8 from each machine → physical network done. No software, no cleverness, just confirm the pipe carries packets.

    3. The first hardware, and the control-plane decision

    I started with two machines on hand:

    • A laptop: i7-8750H, 16GB, GTX 1060, 256GB SSD + HDD. (This becomes legion.)
    • A Lenovo M910q mini-PC: i7-6700T, 16GB, 256GB SSD. (This becomes deus.)

    My initial instinct, straight from the spec, was to make the laptop the control plane since it's the beefier machine. I talked myself out of it, and this was the first genuinely important architectural call of the project:

    The M910q is the better control plane. The reasoning:

    • The i7-6700T is a 35W enterprise part built for 24/7 operation. It idles at ~10–15W. The K3s server process is tiny (it barely touches CPU or RAM), so "beefier" is irrelevant for the control-plane role.
    • The laptop idles far higher (~40W+, more with the GPU) and carries real liabilities for an always-on box: lid-close sleep, aggressive power management, accidental shutdowns.
    • Power math (Singapore, ~S$0.30/kWh at the time): a 50W-idle machine costs ~S$130/year to leave running; the M910q at 15W costs ~S$40/year. For the one node that must never go down, low, boring, and always-on beats fast.

    So the plan flipped: M910q = always-on control plane + worker; laptop = optional burst worker (powered on when I want the extra cores or the GPU). K3s handles nodes joining and leaving gracefully, so the cluster's core would be stable on low-power hardware even with the laptop coming and going, which is closer to how real infrastructure is built anyway (dedicated always-on control plane, not someone's daily-driver laptop).

    (This laptop-is-transient framing held for weeks and shaped many decisions, until I later pulled its battery and made it permanently always-on. But at genesis, "laptop = comes and goes" was the working assumption.)

    4. Why this matters

    None of this is glamorous; it's coax splitters and ping tests. But it's the foundation literally everything else stands on, and two lessons from it recur through the whole project:

    • Solve the physical layer first, completely, before touching software. A flaky MoCA link or a wrong-spec splitter would have looked like a hundred different software bugs later. Getting layer-1 rock-solid up front saved me from chasing ghosts.
    • "Most powerful machine" is the wrong question for a role. The control plane wants reliability and low idle power, not raw horsepower. Matching hardware characteristics to the job (not the spec sheet) is a theme that comes back again and again (GPU placement, storage nodes, thermal-aware scheduling).

    State at the end of this stretch

    • Physical wired LAN into the room via MoCA over coax, through an Omada switch.
    • Two machines identified and roles decided: M910q → control plane, laptop → burst worker.
    • No OS reinstalls or K3s yet; that's next.

    Open / next

    • Install Ubuntu Server on both nodes, set static IPs, bring up K3s.
    • VLAN segmentation on the Omada switch (deferred).
    • A third, more powerful node and a dedicated NAS were already planned (the spec anticipated a Ryzen/desktop power node and a Carousell NAS tower).
