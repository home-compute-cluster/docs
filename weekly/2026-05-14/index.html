    Week 2: OS, Static IPs, and Bringing the Cluster to Life

    Covers roughly 10–14 May 2026. The physical network is done; now the nodes get an OS and K3s.

    With the MoCA LAN solid, this stretch was about turning bare machines into a working K3s cluster: identical OS on every node, static IPs so nothing drifts, the K3s server/agent join, and the first node labels. By the end I had a real two-node cluster serving a test workload.

    1. The OS choice: Ubuntu Server 24.04 LTS on everything

    I standardized on Ubuntu Server 24.04 LTS, headless, SSH-only, on every node. The laptop had actually come to me running Fedora (it was ex-Red Hat hardware), and I deliberately wiped it to match. The reasoning is worth keeping, because "just use what's already on it" was tempting:

    Homogeneity is worth more than convenience. When every node runs the same OS, every troubleshooting session, kernel tweak, and package install is identical across the cluster. Most K3s guides, Helm charts, and Stack Overflow answers assume Ubuntu/Debian. Fedora would have meant dnf vs apt, firewalld vs ufw, and SELinux enabled by default, which actively interferes with K3s networking if you don't configure it. One OS, one mental model. I traded a little setup effort for never having to think "wait, which node is this?" again.

    Also settled here (before installing anything): K3s over MicroK8s. K3s is a single static binary from Rancher/SUSE: it strips cloud-provider cruft, uses SQLite by default (or embedded etcd for HA), bundles Flannel (CNI) and Traefik (ingress), and has a dead-simple one-curl server/agent join model. It's real conformant Kubernetes with the operational fat trimmed, exactly right for modest hardware.

    2. The install pattern (repeated per node)

    For each machine, the same sequence:

    1. BIOS first. Boot order to prioritize the OS SSD; enable AC power recovery / auto-power-on (so a node restarts itself after a power blip); disable sleep/hibernate where the option exists.
    2. A specific BIOS-menu gotcha I hit: the boot menu showed two SSDs, the USB installer, and an "EFI PXE Network" entry. Correct order: USB first (just to run the installer), then the OS SSD, then the other SSD, then PXE last; PXE is network-boot, unneeded, and only adds a boot delay if it's higher.
    3. In the installer's storage menu: the OS goes on the SSD (the install target under "used devices"); the secondary HDD sits in "available devices" untouched; partition and mount it later. Don't configure it during install.
    4. Ubuntu Server install, headless, no desktop. Critical screen: enable "Install OpenSSH server", that's the remote access the whole headless model depends on. Import GitHub SSH keys here if available. Skip all the featured server snaps (K3s comes later, by hand).
    5. Static IP via netplan. DHCP is fine for the first boot, but the nodes need stable addresses so the K3s join target never drifts. Find the interface with ip a / ip link (likely eno1 or enp0s31f6 on this hardware), then edit /etc/netplan/…yaml:

    yaml network: version: 2 ethernets: eno1: # replace with the actual interface name dhcp4: no addresses: - 192.168.1.x/24 # a static IP outside the router's DHCP range routes: - to: default via: 192.168.1.1 nameservers: addresses: [1.1.1.1, 8.8.8.8]

    sudo netplan apply, verify with ip a, confirm internet with ping 1.1.1.1. 4. SSH in from my daily driver, then unplug monitor and keyboard; the node is now headless and remote-managed. 5. Housekeeping: sudo apt update && sudo apt upgrade -y, and sudo timedatectl set-timezone Asia/Singapore.

    3. The laptop's extra steps

    The laptop (soon legion) needed handling the others didn't, because at this stage it was still meant to be a come-and-go burst node:

    • Disable lid-close suspend: otherwise closing the lid kills the node. In /etc/systemd/logind.conf: HandleLidSwitch=ignore HandleLidSwitchExternalPower=ignore HandleLidSwitchDocked=ignore then sudo systemctl restart systemd-logind.
    • Disable the discrete GTX 1060. It just burns 5–20W idle if I'm not using it for GPU work. Either blacklist the modules (nouveau/nvidia in /etc/modprobe.d/, then update-initramfs -u), or (the cleaner route I took) envycontrol -s integrated. Reversible later when I actually want NVENC for Jellyfin.
    • On the battery question: at this point I decided not to remove it. The Legion's battery is internal (non-trivial to pull), modern charge controllers handle being plugged in fine, and the battery is a graceful-shutdown buffer against power flicker. (I reversed this much later, pulling it to make legion truly always-on, but at genesis, leave-it-in was the call.)

    4. Bringing up K3s

    The join model is as simple as advertised.

    Server (on the M910q / deus):

    curl -sfL https://get.k3s.io | sh -

    This installs K3s with the control plane and worker enabled by default (no --disable-agent), which is what I want since deus is a permanent worker too. Then:

    sudo kubectl get nodes                              # deus, Ready
sudo cat /var/lib/rancher/k3s/server/node-token     # grab the join token

    Agent (on the laptop / legion):

    curl -sfL https://get.k3s.io | K3S_URL=https://<deus-ip>:6443 K3S_TOKEN=<token> sh -

    Verify from deus: kubectl get nodes shows both nodes Ready. Two-node cluster alive.

    5. First node labels and a test workload

    Immediately after the join, I labelled the nodes so scheduling intent was baked in from the start rather than bolted on later:

    kubectl label node <deus>   node-type=always-on
kubectl label node <legion> node-type=on-demand
kubectl label node <legion> workload-type=stateless-only   # no stateful pods here

    The stateless-only intent on legion follows directly from the "laptop comes and goes" assumption: no Longhorn replicas, no stateful workloads on a node that might leave. (The plan also anticipated laptop taints, node-role=on-demand:NoSchedule with tolerations only on burst workloads, using soft preferredDuringScheduling affinity for most workloads so the cluster stays flexible if a node drops.)

    Then a throwaway test to confirm health:

    kubectl create deployment test-nginx --image=nginx --replicas=2
kubectl expose deployment test-nginx --port=80 --type=NodePort
kubectl get pods -o wide     # one pod per node

    Hitting the NodePort from another LAN device served the nginx welcome page → cluster genuinely works end to end.

    6. Node identities (the names that stick)

    The naming convention that runs through everything from here:

    • deus: M910q, control plane, 192.168.1.250.
    • legion: the laptop worker, 192.168.1.249.
    • nebula: the desktop/NAS node, 192.168.1.248 (acquired around now; brought fully online shortly after, see Week 0B).

    Static IPs live in the 192.168.1.248–250 range (a small reserved block at the top of the subnet), well clear of the router's DHCP pool.

    State at the end of this stretch

    • Ubuntu Server 24.04 on every node, homogeneous.
    • Static IPs via netplan; headless SSH management.
    • K3s server on deus, legion joined as agent; two nodes Ready.
    • First labels applied; test nginx workload served over NodePort.
    • Node names and IP scheme fixed: deus/.250, legion/.249, nebula/.248.
