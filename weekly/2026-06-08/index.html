    Week 4: Planning Baseline and the First Real Questions

    Covers roughly the week of 8 June 2026.

    This is where I'm starting the written record. By this point the cluster wasn't a blank sheet. I'd already planned it out, bought the hardware, and had ZFS and Seafile running on nebula. So this first week is less "day one" and more "the point where I started asking the questions that actually shaped the build."

    Where things stood when I started writing this down

    Three nodes, all on Ubuntu Server, all meant to be always-on:

    • deus: Lenovo M910q at 192.168.1.250. This is the control plane. It's the small always-on box, so anything that has to never go down lives here.
    • nebula: the i7-6700K desktop at 192.168.1.248. It has 24GB RAM, a GTX 1080, and it's my NAS. ZFS pool tank lives here, and Seafile runs on it via Docker Compose.
    • legion: a laptop at 192.168.1.249 with a GTX 1060. Early on I was still thinking of it as a "transient" node that might not always be up. That assumption changed later (I pulled the battery and it's now always-on), but at this point I was still treating it as flaky.

    The guiding principle I'd already settled on: NAS owns data, K3s owns services. Seafile is the deliberate exception. It sits on Compose on nebula because it's a data-safety thing and I didn't want it depending on the cluster being healthy.

    The Jellyfin / GPU question

    The first real architecture tension I hit. I want Jellyfin to be a K3s workload: it's a good portfolio artifact, it's the kind of thing that shows I can run a real service on the cluster. But GPU transcoding wants a GPU, and the GTX 1080 is in nebula, which is a Compose host, not a K3s node.

    So there's a pull: the convenient place to run Jellyfin (where the good GPU is) is exactly the place that breaks my "K3s owns services" thesis, the same way Seafile already does.

    What I learned digging into this:

    • GPU transcoding matters because it offloads the decode/encode work onto fixed-function NVENC/NVDEC silicon instead of hammering the CPU. That's what lets you run several simultaneous streams without the CPU falling over, and it's far more power-efficient.
    • Consumer GeForce cards have a driver-enforced 3-session NVENC cap. The 1080 included. There's a community patch that lifts it, which is worth remembering if I ever push past three concurrent transcodes.

    I didn't resolve the placement question this week, neither was this service actually crucial for the cluster. The honest answer was: defer it until I'm actually deploying Jellyfin, because CI/CD was the more urgent next step. It's still an open question, legion has a GTX 1060 and is a K3s node, so GPU scheduling on legion (via the NVIDIA device plugin) is the alternative to caving and putting Jellyfin on nebula/Compose.

    The ArgoCD SSH port-forward gap

    Right as I was about to start the CI/CD work, I caught a gap in my own setup guide. The guide said "run kubectl port-forward and open localhost:8080 in a browser." That instruction quietly assumes kubectl is running on my laptop. But I was doing everything over SSH into deus, so localhost there is deus's loopback, not my laptop's. The browser on my laptop can't reach a port that's only bound on deus's loopback.

    This is the SSH-localhost trap and it bit me before I'd even really started. Three ways out:

    1. SSH tunnel: ssh -L 8080:localhost:8080 leifsen@192.168.1.250 chains my laptop's localhost through to the port-forward running on deus. Fastest for a one-off check.
    2. Bind to all interfaces: kubectl port-forward --address 0.0.0.0 ... then hit deus's LAN IP directly.
    3. Run kubectl locally: copy deus's kubeconfig (/etc/rancher/k3s/k3s.yaml) to the laptop and change the server: field from 127.0.0.1 to 192.168.1.250. This is the clean long-term fix and it means I stop SSHing in for routine kubectl work entirely.

    I flagged option 3 as the real answer, and it's exactly what I set up properly a couple of weeks later.

    What I decided this week

    • Jellyfin placement: deferred, revisit at deploy time. Don't cave to nebula reflexively; legion + NVIDIA device plugin is the K3s-honest path.
    • Next focus: CI/CD. Everything else waits behind getting a real git push → deploy loop working.
    • Cluster access: move to a local kubeconfig so I'm not trapped in SSH.
