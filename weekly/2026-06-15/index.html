    Week 5: CI/CD Goes Live, Networking Gets Real, Dev Containers Appear

    Covers roughly 10–15 June 2026. This was the heaviest week by far.

    Four big things landed this week: the full GitOps pipeline, the decision to add WireGuard/Tailscale alongside Cloudflare, the first dev container (with a nasty security surprise), plus some hardware and cost sanity-checking. I'll take them in order.

    1. The full CI/CD pipeline: the centerpiece

    This is the thing I'd been building toward. The goal was a working loop:

    git push → GitHub Actions builds image → ghcr.io → ArgoCD syncs → pod rolls over

    I built it from ArgoCD upward rather than trying to wire the whole thing at once. (Claude and I initially got tangled trying to do it top-down; I flagged the confusion and we restarted from "get ArgoCD reconciling something first," which was the right call.)

    The order it actually went

    1. Expose ArgoCD via a Traefik IngressRoute and a Cloudflare tunnel. deus runs its own cloudflared systemd daemon, separate from the one on nebula that serves Seafile. The tunnel points at localhost:80 (Traefik), hostname argocd.packetcraft.dev.
    2. Beat the .dev HSTS problem. .dev is HSTS-preloaded, so browsers refuse self-signed certs outright. The fix is to route through the Cloudflare tunnel, which terminates TLS at Cloudflare's edge with a real cert. This is why the tunnel isn't optional for .dev domains; it's not just convenience.
    3. Validate the reconciliation loop with a throwaway guestbook Application before trusting it with anything real.
    4. Wire the two-repo pipeline properly.

    The two-repo pattern (and why it has to be two)

    • BarneyLaw/nginx-app: source + the CI workflow.
    • BarneyLaw/homelab-cicd-config: the Kustomize manifests ArgoCD watches.

    The reason it's two repos and not one: CI writes back to the config repo. If the app repo and the config repo were the same repo, that write-back commit would re-trigger CI, which would write back again, an infinite build loop. Splitting them breaks the loop. CI writes to config; ArgoCD reads from config; the app repo is never touched by automation.

    The seam between them is the Kustomize images: block. CI runs kustomize edit set image ...=<image>:<sha> which surgically rewrites the tag. ArgoCD sees the commit and applies it. I never hand-edit the image line.

    Bugs I hit and fixed (all real, all annoying)

    • Config repo name mismatch: the workflow referenced homelab-config but the repo is homelab-cicd-config. Checkout failed until I fixed the name.
    • Uppercase owner in the ghcr image: BarneyLaw vs required barneylaw. ghcr.io rejects uppercase repo names, and worse, kustomize edit set image does a case-sensitive string match, so a case mismatch silently matches nothing and the tag never updates. Fixed by forcing lowercase with tr in the workflow.
    • Swapped file contents between kustomization.yaml and service.yaml. Kustomize specifically reads the file named kustomization.yaml, so swapping contents breaks it silently.

    Credentials: the part that's easy to get wrong

    Three boundaries, each needs a credential only when it crosses into private:

    • CI → ghcr.io (push): built-in GITHUB_TOKEN + declaring packages: write. No manual setup.
    • CI → config repo (write tag): CONFIG_REPO_TOKEN, a fine-grained PAT scoped to only homelab-cicd-config, Contents read/write, nothing else. This is the one I have to make by hand. One PAT works for every app repo since they all write to the same config repo; I just add it as a secret in each.
    • Cluster → ghcr.io (pull): only needed if the package is private. Start by making it public to validate the loop, switch to an image pull secret later.

    By the end of the session I had a green end-to-end sync visible in the ArgoCD UI, and I turned the whole thing into a generalized setup guide (cicd-pipeline-setup-guide.md) so standing up any new service is a checklist, not a re-derivation.

    CI at scale (a follow-up question)

    I asked whether ten different code-server toolchain variants (React, Flutter, Java, etc.) would need ten repos. Answer: no, one app repo with a build matrix. The two-repo split is source-vs-config, not one-repo-per-image. To keep build times sane at that scale:

    • Path-based filtering (paths: triggers + dorny/paths-filter) so only changed variants rebuild.
    • Shared base image: one base/Dockerfile with code-server + common tools, per-toolchain Dockerfiles do FROM base.
    • GHA layer caching with scoped cache-from/cache-to (type=gha).
    • Matrix jobs run parallel (up to 20 on free tier), so a full rebuild's wall-clock is roughly one build. The catch is free-tier minutes get eaten when the base changes; Flutter's SDK is the specific slow layer to order carefully.

    2. Networking: Cloudflare Tunnel isn't enough on its own

    I'd noticed the Cloudflare Tunnel is slow for bulk transfers. That's not a misconfiguration; it's structural. Traffic hairpins out to a Cloudflare edge PoP and back, so file transfers (Seafile, eventually Jellyfin, obsync) pay a detour.

    The original reason I was on Cloudflare Tunnel at all: Singtel gives me a locked router with no port-forwarding or DHCP control, so inbound ports weren't an option. The tunnel dials outbound, which sidesteps that.

    The plan that came out of this was a hybrid split:

    • Cloudflare Tunnel stays for low-bandwidth public services: the planned Hugo/Astro docs site, the ArgoCD UI. It's a dumb pipe and that's fine for those.
    • WireGuard / Tailscale for high-throughput stuff: Seafile, Jellyfin, obsync, bulk transfers.

    Options weighed:

    1. WireGuard mesh via a cheap VPS relay (home dials out, no inbound ports needed).
    2. Tailscale / Headscale: WireGuard under the hood, but with built-in NAT traversal and DERP relay fallback. Identified as the lowest-effort high-bandwidth option specifically because of the locked-router constraint.
    3. Cloudflare WARP-to-Tunnel private routing, noted as not solving the bandwidth problem (still hairpins).

    The principle I locked in here: Cloudflare Tunnel = dumb pipe, Traefik = routing brain. Both Cloudflare and Tailscale are just ingress pipes feeding the same Traefik routing layer. This becomes a recurring rule.

    3. The first dev container, and a security surprise

    I built a dynamically-scheduled VS Code dev container (code-server) on the cluster through the GitOps pipeline. Two repos again: code-server-app (source + CI) and the shared config repo. The point was a reproducible dev environment and a sandbox for running an autonomous coding agent (OpenAI Codex).

    This session was a gauntlet of small real failures, each with a lesson:

    1. CI didn't trigger: code-server-app was initialized locally with a master default branch, but the workflow watched main. Each repo tracks its branch independently; my config repo uses main, this one came up master.
    2. VS Code CLI Dockerfile layer 404'd: the code.visualstudio.com/sha/... redirect endpoint is fragile. Fixed by switching to the stable update.code.visualstudio.com/latest/cli-linux-x64/stable URL.
    3. Crash loop: entrypoint.sh was committed from Windows without the executable bit. Fixed with --chmod=755 on the COPY.
    4. code tunnel rejected --random-name=false: it's a presence/absence boolean flag, not one that takes a value.
    5. Auth didn't survive pod restarts: the PVC was mounted at ~/.vscode-cli but the CLI actually writes to ~/.vscode/cli. Found by running find /home/dev/.vscode -maxdepth 3 instead of assuming the path.
    6. Tunnel re-registered as a new service every deploy: fixed by pinning the pod to nebula with nodeSelector and correcting the PVC mountPath.

    Codex's ChatGPT login needs a browser callback a headless pod can't do, so I transplanted the credential file: scp to deus, then kubectl cp into the pod's persistent ~/.codex PVC.

    The ambient authority leak

    The scary one. The container could git push to GitHub with no configured credentials, no stored token, a clean remote URL. That shouldn't be possible.

    Cause: GIT_ASKPASS and related VSCODE_GIT_* env vars set by the VS Code server. They broker git credential requests through my signed-in editor session, giving the agent implicit, account-wide GitHub write access instead of repo-scoped access. All my careful network and filesystem scoping didn't matter, because the credential came in through a side channel inherited from the editor.

    The fix (fine-grained single-repo PAT via a Kubernetes Secret + unsetting the VS Code git env vars) I deliberately deferred: current state is fine for supervised runs only. I wrote up twelve numbered lessons and an open-items checklist. This leak comes back the following week.

    Storage decision baked in here

    The pod is pinned to nebula, not dynamically placed, because local-path PVs are node-bound and a stateful interactive workload needs either node-independent storage or a pin. Dynamic placement is for stateless services. Longhorn is the correct long-term fix to get free placement back with persistent storage, and it's now unblocked since the NAS drives are in with ZFS running. The workspace itself stays ephemeral (emptyDir, wiped on restart); only the auth dirs (~/.vscode/cli, ~/.codex) persist on small 64Mi PVCs.

    4. Hardware and cost sanity checks

    Two side conversations that informed direction:

    Cheap interconnect / more nodes. The cluster had drifted from "many cheap nodes" toward "fewer, more powerful nodes." To reintroduce breadth without breaking my single-arch (linux/amd64) images, the zero-friction path is Intel N100/N150 mini-PCs (Beelink S12 Pro, GMKtec G3, Trigkey) or used USFF enterprise boxes (ThinkCentre M710q/M910q, HP EliteDesk 800 G3/G4). ARM SBCs like Raspberry Pis would force multi-arch builds via docker buildx, avoidable friction. (I also floated a separate 10-node Pi cluster for CS3210 parallel-computing coursework; for MPI-from-source the arch concern disappears, but old Pis with 100Mbit ethernet would bottleneck collective ops; Pi 3B+/4 with gigabit is the educational choice.)

    AWS-equivalent cost. As a sanity check on whether owning hardware was worth it: the cluster (deus 4c/16GB, nebula 8c/24GB+1080, legion 6c/16GB+1060, ~1TB ZFS) maps to roughly $970/month / $11,600/year on-demand, ~$7,000/year on 1-year reserved. My entire hardware build cost less than one month of that bill. Electricity is ~S$15–35/month for the always-on nodes, which is fine. The broader lesson: cloud wins for spiky/unpredictable load, owned hardware wins for steady high-utilization baselines, which is exactly the deus-always-on / burst-elsewhere shape I already have.

    What I locked in this week

    • CI/CD pipeline is live and documented. Two-repo pattern, SHA-tagged images, ArgoCD self-heal/prune.
    • Hybrid networking direction: Cloudflare for public/low-bandwidth, WireGuard/Tailscale for bulk. Tailscale is the front-runner given the locked router.
    • Dev container running but with a known, deferred credential leak. Supervised use only until fixed.
    • Longhorn is the next storage unlock now that NAS drives are in.
