    Week 6: Clean Cluster Access, Documentation, Closing the Security Hole, WireGuard

    Covers roughly 15–21 June 2026.

    This week was about consolidating. The pipeline worked, so now I made the cluster pleasant to operate (proper kubectl access), wrote down what I'd learned (a run of reference guides), finally closed the credential leak from last week, and got WireGuard actually deployed.

    1. Proper cluster access from my real machine

    I was tired of SSHing into nodes for everything. The conceptual split I settled on and want to keep straight:

    • Node-level work → SSH. Anything below K3s: the OS, systemd, ZFS, installing the k3s binary itself.
    • Cluster-level work → kubectl against the API server. Deploying, debugging, inspecting workloads.

    These are different layers and I shouldn't be reaching for SSH to do cluster-level things.

    The Windows/WSL setup

    I work from a Windows PC, doing terminal and kubectl work in WSL. Setup:

    • Install just kubectl on the client (not the whole k3s binary): winget install -e --id Kubernetes.kubectl.
    • Bootstrap the kubeconfig in one shot: ssh leifsen@192.168.1.250 "sudo cat /etc/rancher/k3s/k3s.yaml" > ~/.kube/config
    • Edit the server: field from https://127.0.0.1:6443 to https://192.168.1.250:6443.
    • Added k9s (winget install Derailed.k9s) for a terminal UI over the cluster.

    Two gotchas that will silently break this:

    1. TLS SAN: the API server's cert has to include 192.168.1.250 in its SANs, or kubectl refuses the connection. Fixed on deus via --tls-san in the k3s server config; this is a server-side fix, not something I can patch on the client.
    2. WARP split-tunnel: for remote (off-LAN) access, WARP must not exclude RFC1918 ranges, or the private route to 192.168.1.0/24 gets dropped. The neat payoff: with the tunnel advertising the private route, the same kubeconfig works both on-LAN and remotely with no reconfiguration.

    The workflow rule this reinforces

    Because ArgoCD runs with selfHeal: true, any manual kubectl edit on a managed workload gets reverted. So:

    • Managed app changes → git push to the config repo. That's the source of truth.
    • kubectl / k9s → live debugging and cluster ops only.

    Don't fight self-heal. If I want a change to stick, it goes in git.

    2. A run of reference documentation

    I wrote several guides this week, in the same house style as the CI/CD guide (ASCII diagrams, comparison tables, blockquote warnings, dependency-ordered checklists, a command reference at the end). These are for future-me.

    • Dockerfile guide: every major instruction, the layer-caching mental model, the cleanup-in-the-same-RUN rule, dependency-before-source ordering, base image trade-offs (scratch / distroless / alpine / -slim), multi-stage patterns. Tailored to my actual projects: the obsync-server binary with its serve | migrate | health subcommands (hence the ENTRYPOINT ["/server"] + CMD ["serve"] pattern and the CGO_ENABLED=0 requirement for a scratch final stage), plus the custom L4/L7 proxy and scheduler. Noted the Node→nginx multi-stage pattern for the upcoming static docs site, and that off-the-shelf images (Jellyfin, Grafana) skip CI entirely.

    • K3s / Kubernetes guide: fourteen sections answering "are K3s and Kubernetes the same thing" and everything downstream: the reconciliation mental model, the object hierarchy, kubectl, manifest anatomy, scheduling (nodeSelector, affinity, taints/tolerations, resource requests), networking (Service types, the Cloudflare Tunnel ingress path, CoreDNS, Flannel), storage (PVC/PV/SC, local-path vs planned Longhorn), ConfigMaps/Secrets, probes, Helm vs Kustomize, K3s-specific ops. Every concept tied back to my actual architecture. Flagged the NVIDIA device plugin as the missing link for GPU scheduling on legion, which is the key that would let Jellyfin run on legion in-cluster instead of caving to nebula/Compose.

    • Observability setup guide (this leans into next week's monitoring work, but the writing happened here). Covered the Prometheus Operator's ServiceMonitor CRD model and the serviceMonitorSelector label-matching gotcha: if the selector doesn't match your ServiceMonitor's labels, scrapes silently fail. The RED method (Rate, Errors, Duration) as the per-service dashboard framework. Traefik metrics via K3s HelmChartConfig (with addRoutersLabels / addServicesLabels for per-hostname breakdown). Two open decisions written down explicitly: the permissive serviceMonitorSelectorNilUsesHelmValues: false toggle vs labelling every ServiceMonitor, and PVC vs GitOps-managed ConfigMaps for Grafana dashboards (I lean ConfigMaps, consistent with "GitHub as source of truth"). Decided to start by instrumenting existing services (Traefik, ArgoCD, Seafile) rather than new ones. KEDA autoscaling and the Seafile cross-boundary scrape are deferred as their own projects.

    3. Closing the dev container security hole

    Back to the GIT_ASKPASS leak from last week. This session I did the full upgrade pass on the dev container and actually closed it.

    First, some housekeeping bugs found live:

    • A missing YAML --- separator meant the Codex auth PVC (code-server-codex-auth) was never created; only one PVC existed instead of two. So Codex credentials were living on ephemeral storage, one pod restart from being lost. Fixed the separator, backed up auth.json, committed the PVC fix.
    • Confirmed the tunnel auth was correctly persisted at ~/.vscode/cli.

    The architectural decision: one container = one project

    Each dev environment gets its own repo and its own scoped GitHub PAT. I built a generator (new-project-env.sh + four YAML templates in code-server-app/templates/), derived faithfully from the live deployment rather than a speculative redesign. It takes <PROJECT>, <REPO_URL>, branch, tunnel name, image name; substitutes placeholders; and prints the exact out-of-band steps (PAT creation, scope verification). First instantiation: budget-app-dev.

    Two distinct security holes, confirmed by testing

    1. The env-var leak is structural. GIT_ASKPASS / VSCODE_GIT_* are injected by the VS Code tunnel server into child shells after the entrypoint runs, so unsetting them in the entrypoint can't reach the agent's shells. I confirmed the account-wide access with an isolation test: GIT_ASKPASS= git -c core.askPass= ls-remote still returned refs.
    2. The PAT was scoped too broadly ("all repositories"), so even without the env leak the token itself was over-privileged.

    The fixes are independent:

    • Re-mint the PAT scoped to a single repo (GitHub-side, no rebuild needed). This is the load-bearing security fix.
    • Dockerfile changes to close the env leak everywhere shells can start:
    • /etc/profile.d/devbox-path.sh for interactive login shells.
    • /etc/devbox-bashenv.sh referenced via ENV BASH_ENV= for non-interactive bash -c shells; this is the path Codex actually uses, which is why entrypoint-only unsets missed it.
    • git config --system core.askPass "" at system level as environment-independent defense.

    Toolchain upgrades (same session)

    The code-server-app image grew a Flutter environment for a budget-app project: Flutter SDK 3.27.1 (added as the dev user, precache --universal), OpenJDK 17, Android cmdline-tools with the critical cmdline-tools/latest/ layout fix that sdkmanager requires, and platform-tools (adb) pulled non-fatally at build. Heavy Android bits (platforms;android-34, build-tools) deliberately deferred to runtime via sdkmanager; I chose "Java + cmdline-tools only" explicitly. System Gradle omitted on purpose since Flutter projects vendor their own gradlew. The image stays a monolith for now rather than splitting into per-toolchain variants, a deliberate "get it running" choice.

    4. WireGuard actually gets deployed

    Following the hybrid-networking plan from last week, I moved on WireGuard for the bulk-transfer path. The question that gates everything: is my Singtel line behind CGNAT, or do I have a real public IP? A fully home-owned WireGuard setup (no VPS) only works with a real routable IP.

    I shared my WAN IP and it checked out; it belongs to the SINGTEL-FIBRE 42.60.0.0–42.61.255.255 allocation (SingNET Broadband), a genuine public IP, not in the 100.64.x.x CGNAT range. So a no-VPS setup is possible in principle.

    The remaining unknown: will the locked Singtel ONR forward inbound UDP 51820 to deus? I tried testing with nc -u from my phone on mobile data and got nothing, but that result is inconclusive, not a failure. The most likely reason for silence was that I hadn't actually added a port-forward rule to the ONR yet, not that the ONR can't forward.

    The better approach, which I took: stop messing with nc and just deploy the real WireGuard config on deus and the phone, then use a successful handshake (sudo wg show) as the definitive port-reachability test. That collapses the diagnostic and the deployment into one step. Also flagged: if the IP turns out dynamic, a Cloudflare DNS record (vpn.packetcraft.dev) updated via the Cloudflare API is the DDNS workaround.

    (End state on the network stack, consolidated later: Tailscale subnet router on deus advertising 192.168.1.0/24, plus WireGuard on UDP 51820 port-forwarded through the ONR as the high-throughput admin path. WireGuard on UDP 51820 is confirmed working through the ONR; the real IP made it possible.)

    5. Terraform vs Ansible: deciding the IaC layer

    I asked whether to adopt Terraform or Ansible, and when. The distinction: Terraform provisions infrastructure via APIs; Ansible configures machines that already exist.

    Decision: Ansible is the higher-value tool for me, because my manual-over-SSH work is exactly node/OS-layer config: k3s install with --tls-san, systemd units, ZFS setup, sudoers, WoL, kubeconfig distribution. The k3s-ansible role is a maintained starting point. Terraform is only narrowly useful here, for Cloudflare resources (tunnels, DNS, Zero Trust) and maybe GitHub config, but not for compute, since I have no API-driven provisioning.

    The layering boundary I locked in: Ansible handles below-K3s node state, ArgoCD owns in-cluster workloads, and the two must not overlap.

    On timing: don't adopt either mid-build. Write playbooks retroactively the next time I rebuild or add a node: capture the state when I'm already touching it, rather than stopping everything to Ansible-ify a working cluster. (Importing existing Cloudflare config into Terraform state is fiddly and better done incrementally anyway.)

    What I locked in this week

    • Clean kubectl/k9s access from WSL, same config on-LAN and remote. TLS SAN and WARP split-tunnel are the two things that break it.
    • A shelf of reference guides (Docker, K3s, observability) in a consistent style.
    • Dev container security actually fixed: single-repo PAT (load-bearing) plus Dockerfile-level env-var closure at all shell entry points.
    • WireGuard deployed, using the handshake itself as the port test. Real public IP confirmed.
    • Ansible chosen as the IaC layer, to be written retroactively; ArgoCD/Ansible boundary drawn.
