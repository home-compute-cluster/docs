    Week 7: Ingress Architecture, Patch Management, and Longhorn

    Covers roughly 25–26 June 2026.

    Shorter week in terms of number of sessions, but it settled two architectural rules I'd been circling (ingress and patching) and finally kicked off Longhorn, which had been "next" for a while.

    1. Should I run two reverse proxies?

    The Tailscale work raised a real question: I've got Traefik handling traffic from the Cloudflare tunnels. Should I stand up a separate nginx to handle traffic coming in over Tailscale?

    The answer I landed on: the two-pipe, one-brain model. Two ingress paths (Cloudflare and Tailscale) is fine, but they should both feed the same Traefik routing layer. Cloudflare and Tailscale are dumb pipes; Traefik is the single routing brain. This is the same principle from the networking week, now stated as a hard rule.

    The important distinction, when is a second proxy acceptable:

    • Not acceptable: a second general-purpose in-cluster ingress controller running in parallel with Traefik. That's two brains, and routing logic fragments across both. Avoid.
    • Acceptable: nginx as an app-local front door for a self-contained stack that runs outside K3s. The obsync v2 design is exactly this: nginx scoped to the WireGuard interface, fronting the specific obsync-server/Postgres stack. That's analogous to how Seafile runs on Compose outside the cluster. The nginx there isn't a general ingress; it's part of one stack and never allowed to become a second general-purpose front door.

    So the rule: per-app proxies must be scoped to their stack only. One general-purpose routing brain (Traefik), full stop.

    2. Patch management without blind cron jobs

    I asked how to handle the endless stream of OS updates without running risky "blind upgrade" cron jobs. The framing that made it click: updates fall into three layers, each with its own strategy.

    Host OS packages

    • unattended-upgrades scoped to security updates only, with auto-reboot disabled. I don't want a node silently rebooting itself mid-workload.
    • needrestart to identify which patches actually need a reboot, so reboots are a deliberate decision.
    • kured (Kubernetes Reboot Daemon) to automate the cordon → drain → reboot → uncordon cycle safely across the cluster when a reboot is needed. It coordinates so nodes don't all go down at once.

    K3s itself

    Version-pin and upgrade manually and deliberately. No automation here; a k3s version bump is not something I want happening unattended.

    In-cluster workloads

    My GitOps loop already handles this cleanly. The addition: Renovate to surface new image tags and Helm chart versions as pull requests against homelab-cicd-config, which then feed the normal ArgoCD reconciliation. So updates become reviewable PRs, not surprises.

    The nebula nuance

    nebula is the awkward node: it runs Seafile, ZFS, and Compose workloads outside K3s. That means:

    • kured can't cordon/drain it the way it handles the K3s nodes, so suppressing auto-reboot matters most here.
    • Compose services on nebula should use restart: unless-stopped for resilience across any reboot that does happen.

    (Renovate is noted as planned, not yet set up.)

    3. sudoedit: a small quality-of-life recovery

    I remembered installing something in a past session that let me edit privileged files with a normal editor instead of sudo nvim, and wanted to find it. Turns out it wasn't a thing I installed; it's sudoedit, a built-in. It copies the privileged file to a temp location, lets me edit it as a normal user (with my own Neovim/LazyVim config, EDITOR=nvim), then writes it back with elevated privileges. Nothing to install; just use sudoedit /path/to/file. Worth writing down so I don't hunt for it again.

    4. Longhorn: distributed storage, finally started

    The motivation has been consistent since the dev-container week: K3s's default local-path StorageClass pins stateful pods to a node via nodeSelector (the code-server pin to nebula is the live example). Longhorn gives replicated, distributed block storage with a proper CSI driver, which lets pods schedule node-independently while keeping persistent state.

    Prerequisites and the multipathd snag

    Ran the official environment check:

    curl -sSfL https://raw.githubusercontent.com/longhorn/longhorn/v1.8.1/scripts/environment_check.sh | bash

    It flagged multipathd running on all three nodes, a known Longhorn breakage. multipath is an enterprise SAN feature with zero applicability to my directly-attached storage. Fix is either blacklisting sd* devices in /etc/multipath.conf or disabling the daemon outright (systemctl disable --now multipathd).

    A subtlety that tripped me: deus already had the correct blacklist stanza in /etc/multipath.conf, but the warning persisted. That's because the environment check warns on the daemon being present at all, regardless of config, so I needed a reload/restart or a full disable to clear it, not just the right config file.

    Longhorn installed after that and the web UI came up.

    The critical prerequisite gap: Longhorn cannot use ZFS

    The big correctness point. Longhorn can't use a ZFS dataset as its data path. It needs a dedicated disk formatted ext4 or XFS, mounted at a stable path (e.g. /var/lib/longhorn-disk). So the ZFS tank mirror on nebula is not usable for Longhorn; I need separate disks.

    This is why the plan settled the way it did:

    • nebula: dedicated Longhorn NVMe disk (separate from the ZFS pool), replica target.
    • legion: its 500GB WD Red SA500 SATA SSD partitioned, ~400GB for Longhorn at /var/lib/longhorn-disk-sda, replica target.
    • deus: no Longhorn replicas. deus overheats, and I don't want to add storage-replication load to it. Thermal management drives workload placement here.
    • 2 replicas (nebula NVMe + legion SATA). Two is the meaningful-redundancy floor; below two, Longhorn gives no node-independent redundancy at all.

    Related things flagged

    • Security: the Longhorn UI was exposed via a Cloudflare tunnel without auth. Securing it got deferred to the next day, but it's noted.
    • Backup target: should point at an NFS share on nebula's ZFS tank pool, and this should be configured before any database holds meaningful data.
    • Replica count honesty: set it based on how many nodes actually have dedicated Longhorn disks. A single-node setup forces replica count 1 or produces perpetually degraded volumes; don't pretend to redundancy I don't have.
    • The payoff: once validated with a throwaway PVC, I can finally drop the nodeSelector pin on code-server and let it schedule freely.

    A note on legion's status

    Somewhere around here legion stopped being "transient" in my head. I pulled its battery and it runs all the time now. That's what makes it a legitimate Longhorn replica target and an always-on worker; I should stop treating it as WoL/transient. (Related: MetalLB advertising the Traefik VIP on legion is acceptable precisely because legion is now always-on.)

    What I locked in this week

    • Ingress rule: two pipes (Cloudflare + Tailscale), one brain (Traefik). App-local proxies only for out-of-cluster stacks, scoped to that stack.
    • Patch strategy: three layers: unattended-upgrades (security, no reboot) + kured for host; manual pinned upgrades for K3s; Renovate PRs for workloads. nebula is the special case.
    • sudoedit for privileged file editing. Built-in, no install.
    • Longhorn installed, 2-replica across nebula NVMe + legion SATA, none on deus (thermal). ZFS-can't-back-Longhorn is the load-bearing constraint.
    • legion promoted from transient to always-on worker.
